## Step 1 — Check coverage map first

Read `reference_coverage_map.md` (if it exists yet — skip this step on a brand-new project with no prior coverage
map) and check whether any behavior from this ticket is already covered.

- If fully covered → tell the user and stop. Do not write duplicate tests.
- If partially covered → identify the gap and proceed only for what's missing.
- If not covered → proceed.

**Never skip this step once a coverage map exists. Duplication wastes tokens and pollutes the suite.**

## Step 3 — Determine test type and target file

Apply the STRICT placement rule before writing a single line:

| Question | Answer | Placement |
|----------|--------|-----------|
| Does this verify a bug was fixed or a new feature introduced by a ticket? | Yes | `tests/regression/` |
| Does this cover a core happy path or critical workflow? | Yes | `tests/smoke-tests/` |

- Group spec files by feature area / portal, mirroring however `pages/` is organized for this project
- **Never mix smoke and regression in the same file.**

Determine the target spec file name. If a relevant spec file already exists for this feature area, add to it. If not, create a new one.

## Step 4 — Explore dev to understand the UI

Use the MCP browser to navigate to `{{DEV_URL}}` (or `{{ADMIN_DEV_URL}}` for admin-side tickets) and verify:

1. The feature/fix is actually deployed on dev (if not, tell the user and stop — do not write tests for undeployed code)
2. The exact element names, labels, and locators needed
3. Any gotchas (loading states, async fetches, disabled states, timing)

Use the project's saved `storageState.json` (and `adminStorageState.json`, if a second role exists) — both are pre-generated by `globalSetup`.

**Always verify on dev. Never write tests based on assumptions about what the UI looks like.**

## Step 5 — Propose test cases

Apply ISTQB principles and the project's test design rules:

- **Single responsibility** — complete the sentence: *"This test verifies that [ONE thing]."* If it needs "and" — split it.
- **Positive paths** — does the happy path work?
- **Negative paths** — are blocked/invalid states enforced?
- **Edge cases** — empty state, boundary values, multiple data samples (Senior QA mindset — never test only one record)
- **Coverage dimensions** — every AC maps to at least one test

Present the proposed test cases as a numbered list:
```
TC0XXX — [action/condition] [expected result]
TC0XXX — [action/condition] [expected result]
```

**Wait for user confirmation before writing any code. Never act unilaterally.**

## Step 6 — Write the tests

Only after the user confirms the proposed test cases.

### Naming conventions — MANDATORY, NO EXCEPTIONS

- **TC IDs**: sequential from last used TC (check the project's inventory/next-task memory for the last TC)
- **Test names**: `[action/condition] [expected result]` — present tense, behavior-focused, clean
  - ✅ `typing "ford" in R1 Financial Entity shows Ford Credit in the dropdown`
  - ❌ `R1 dropdown shows Ford Credit (ACCOUNT-only lender previously filtered out)` — no parenthetical junk
  - ❌ `selecting lender shows modal; Ok dismisses it` — no semicolons, no joining two outcomes
- **describe() block**: NEVER include the ticket ID in the name — it shows in Allure and pollutes the suite
  ```js
  // {{TICKET_PREFIX}}-XXXX
  test.describe('Feature Area — Sub-feature', () => {
  ```
- **Ticket traceability**: put the ticket reference in a comment above the describe block or above each test, not in the name

### Code conventions

- Plain JavaScript (ESM), never TypeScript
- Never use CSS-framework class selectors — use `getByRole`, `getByText`, `getByLabel`
- `beforeEach` readiness gate — always wait for a stable element before running assertions
- Use `pressSequentially` (not `fill`) for inputs that need framework key-event handlers (React, etc.)
- Use `{ exact: true }` when text could partially match something else
- DB setup/teardown via `utils/db.js`'s `createDbClient()` when test data needs to be in a specific state —
  **only if this project has a DB utility configured**; skip this if the app has no direct DB access
- `test.describe.configure({ mode: 'serial' })` only when tests share mutating state
- Page object: if adding locators needed in multiple tests, add them to the relevant page object. If no page object exists for the feature, add locators inline.

### File header

Every spec file must have a header comment block:
```js
// ─────────────────────────────────────────────────────────────────────────────
// [Section number]. [Portal] — [Feature] ([TC range])
//     Uses saved [role] auth state.
// ─────────────────────────────────────────────────────────────────────────────
```

## Step 7 — Run only the new tests

```bash
rm -rf allure-results && npx playwright test [spec-file] --project=chromium 2>&1
```

- **Never run the full suite** to verify new tests — use `--grep` or target the specific spec file
- If tests fail, diagnose and fix before moving on
- After new tests pass, run the full spec file to confirm no regressions in existing tests

## Key rules — never break these

| Rule | Detail |
|------|--------|
| Check coverage map first | Never write a test that already exists |
| Verify on dev before writing | Never assume the UI — always look |
| Test multiple data samples | One passing case ≠ bug fixed. Senior QA mindset: hunt for failures across different data variants |
| Single responsibility | One objective per test — if name needs "and", split it |
| Clean test names | `[action/condition] [expected result]` only — no ticket IDs, no parenthetical notes, no internal jargon |
| No ticket ID in describe() | Put it in a comment instead |
| Regression → regression/ | Smoke → smoke-tests/. Never mix |
| Chromium only | Always `--project=chromium`, never Firefox, unless the project explicitly runs multi-browser |
| Allure always | Generate and open after every run without being asked |
| Ask before writing | Propose tests and wait for confirmation — never act unilaterally |
| Dev env only | Automation always targets the dev environment, never prod |
